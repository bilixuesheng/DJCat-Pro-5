# 服务端在 Admin Console 中自更新

服务端跑在宝塔面板管理的服务器上，以前每次更新都要手动上传文件、再到面板里重启。现在改成在 Admin Console 一键 Server Update：服务端自己从 GitHub 公开仓库下载检查时读到的那个提交，只解压 `server/`；依赖有变化就先装好，再用数据库副本试导入，通过后才替换文件，最后给 gunicorn 主进程发 `SIGHUP` 平滑换 worker。

## Considered Options

- **GitHub Actions 经 SSH 部署**：发版能自动化，但要把能登录服务器的私钥存进 GitHub，服务器还得对 GitHub 全球的 runner 地址开放 SSH。
- **调用宝塔面板 API 重启**：服务端要保存一把能控制整台服务器的面板密钥，换来的只是一次重启。
- **进程退出后靠守护进程拉起**：正在进行的 AI Markdown Conversion 会直接失败。
- **从雨云对象存储下载**：国内访问稳定，但每次发版都要多一步手动上传。实测服务器访问 GitHub 正常（API 0.4 秒，13 MB 压缩包 6 秒）。
- **第三方 GitHub 加速镜像**：下载的是服务端要执行的代码，镜像被篡改就等于服务器被接管。

## Consequences

- 仓库地址写死在代码里，后台表单和设置都改不了。后台密码即使泄露，攻击者最多把服务端更新到已发布的版本，不能让它运行任意代码。
- 是否提供 Server Update 只看 Server Version：main 上的版本号改了才算发布；同版本号的新提交不提示，直到下次改版本号。
- gunicorn 不能开 `preload_app`，否则 `SIGHUP` 不会加载新代码；`graceful_timeout` 要放到 150 秒，否则换下的旧 worker 只等 30 秒就打断进行中的 AI 整理，等于又回到了被否决的「退出重启」。新版若升级了 gunicorn 本身，要在宝塔面板手动重启一次。
- 更新只装管理员确认的那个提交，并先确认它在 main 上：GitHub 按提交号也能取到 fork 里的提交，不核实就绕过了「只能更新到已发布版本」。
- 新代码导入失败会让 gunicorn 主进程退出，后台也随之打不开。所以替换前必须试导入，并且要连数据库副本：导入时就会执行表结构迁移。README 另留一条后台打不开时用的手动回滚命令。
- 第一个带这个功能的版本（1.4.8）只能手动部署。
